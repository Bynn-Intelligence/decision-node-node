# Changelog

## 0.3.0 (unreleased)

Implements version 1.3 of the DecisionNode SDK specification (`SPEC_VERSION` is `"1.3"`).

- The package is `@decisionnode/sdk` (it was `@bynn/decisionnode`): `npm install @decisionnode/sdk` and `import { DecisionNode } from '@decisionnode/sdk'`. An install from GitHub installs under the same name.
- The default model is `decisionnode-moe` (it was `decisionnode-latest`), and the docs and examples use the family ids `decisionnode-moe` and `decisionnode-flash`, which always mean the current release. A pinned release is `decisionnode-<family>-<version>`, as `models()` lists it. The older ids (`decisionnode-1.0`, `decisionnode-1.0-flash`, `decisionnode-latest`, `decisionnode-flash-latest`) are still accepted by the API and sent as given.

- Boosters: `boosters` on `decide`, `check`, `classify`, `score`, `number`, `gate`, `decideMany` requests, batch requests and `checkRequest`, as names (`'age'`), `new Booster(name, { images, require, options })` (sent as `{ name, ... }`, or as the bare name when no setting is given) or the API's own objects, sent in order; each setting is left out of the request when not given, and no `boosters` field is sent when none (or an empty list) are given. `BoosterName` offers `'age'` and `'ai_generated'` and takes any other string. Nothing about boosters is checked before sending; a booster's `options` count toward the request's nesting limit. Sessions take no boosters.
- `Decision.evidence`: one `Evidence` (`version`, `status`, `latencyMs`, `billedCalls`, `results`, `raw`) per booster the request named, by name in the request's order, `null` for a request without boosters. Readings are `AgeReading` (`image`, `faces`, `ageYears`, `low`, `high`, `confidence`; the age fields `null` with no face) and `AiGeneratedReading` (`image`, `generated`, `confidence`, `method`, `topGenerator`, `null` unless the reading says likely generated, `c2paSigner`, and `c2pa`, `untrusted` for Content Credentials that validate but are not trusted); a reading of an unknown booster, or one with a field missing or of the wrong type, is an `UnknownReading` with its raw fields, and the decision does not fail.
- `Decision.usage.boosterTokens` and `Decision.usage.boosters` (`null` when absent).
- `Decision.usage.cost`: what each answer cost in USD, `{ usd, modelUsd, boostersUsd, freeTier }`, read as sent (`usd` is never computed from its parts), `null` when the server sent none. A session's open and each frame reply carry it in their `usage` as received.
- Every error has `boosters`: each booster's status and time by name, read from the `x-decisionnode-boosters` response header (`parseBoostersHeader`), empty when the header is absent. `booster_unknown` and `booster_input_mismatch` are `BadRequestError`s, `booster_not_enabled` a `PermissionDeniedError` (as every 403 that is not a refusal, a suspended workspace's included), and `booster_unavailable` an `OverloadedError`, retried like every 529.
- `RequestTooLargeError` for every 413, never retried. The API takes a request body of at most 25 MiB (26,214,400 bytes): the client measures each body as it would be sent before sending it (inline images and frames included, an image it would upload counted by its upload id) and throws `RequestTooLargeError` (`request_too_large_error`) for one over the limit, on `decide`, the helpers, `decideMany` (none is sent when one is over), each batch line and `checkRequest`. `decideRaw` sends its body as given.
- Fallback: `fallback` (a boolean) on `decide`, the helpers, `decideMany` requests, batch requests and `checkRequest`, sent only when given. `Decision.fallback` is `null` on an ordinary answer and `{ servedModel, requestedModel }` from `x-decisionnode-fallback` and `x-decisionnode-requested-model` when a `decisionnode-moe` request was answered by Flash: the model that answered by its pinned id, the model asked for as the family id (or as the pinned id that was asked); `Decision.model` stays the model that answered. The 529 a `fallback: false` request gets is an `OverloadedError`, retried like every 529.
- An error whose body is not JSON (a page from the service's edge or a proxy, or an empty body) is classed by its status alone, with `errorType` `null`, `requestId` and `reason` from the headers, and the message `HTTP <status> <text>` from a fixed table (`HTTP 413 Content Too Large`), followed by the request id when sent. The page is never read into the error (`body` is `undefined`). A 400 is never a `ContextLimitError` and a 403 never a `RefusalError` without the JSON body; retries are unchanged.
- An image id over 64 characters, counted as Unicode code points, is refused before anything is sent: `BadRequestError` `api_usage_error`, `Image <n>: its id is longer than 64 characters.`
- Fine-tuned models: a name such as `decisionnode-moe@acme/fraud` or `...:3` is sent as given in `model`, and `Decision.model` is the pinned name that answered. `ModelInfo` gains `fineTuned`, `base`, `adapterVersion` and `status`, each `null` on a catalogue entry.
- Batch results read some time after `results()` no longer come back empty: the client holds the response with its body until the results are read, since Node's fetch cancels the body of a response that is garbage collected first.
- Booster readings `FaceDetectionReading` (`image`, `faces`, `detections`, each `{ box, confidence }`) and `FaceRecognitionReading` (`image`, `faces`, `matches`, each `{ box, score, collection, reference, name, label }`, `name` and `label` `null` when absent), a box `{ x1, y1, x2, y2 }` as sent; a reading with a field missing or of the wrong type is an `UnknownReading`. `BoosterSettings` types `face_recognition`'s `collection` and `threshold`, sent as given.
- `FaceRecognitionReading.collectionName` (an own collection's display name) and, on each match, `collectionName` (an own collection's display name or id, a public collection's id) and `metadata` (an own item's metadata object as sent), each `null` when absent, never `{}`; a reading whose `collection_name` is not a string, or a match whose `collection_name` is not a string or whose `metadata` is not an object, is an `UnknownReading`.
- Collections of faces: `client.collections.create({ name, type })` (`type` `face` by default), `list()`, `get(id)`, `delete(id)`, `enroll(id, { image, reference, label })` (the image sent as a decision sends it), `listItems(id, { offset, limit })` and `deleteItem(id, itemId)`, each returning the API's object as sent. `create` and `enroll` send an `Idempotency-Key`, a new UUID per call and the same on every attempt of it, so the API creates, enrolls and bills once; they retry like any call, and also on a 409 `idempotency_in_progress` after its `Retry-After`, while a 409 `idempotency_key_reused` is thrown and never retried. A type other than `face`, a name not 1 to 80 characters, a reference not 1 to 64 of `A-Z a-z 0-9 _ . : -`, a label over 128 characters and an `offset` or `limit` out of range are refused before anything is sent; of an enrolled image only a URL is checked here, and every other fault of the picture is the API's 422 `image_unreadable`.
- Collections items described and edited: `enroll` takes `metadata`, and `updateItem(id, itemId, { reference, label, metadata })` sends `PATCH` with only the fields given (`label: null` clears the label, `metadata` replaces the whole object), with an `Idempotency-Key` and retried as `create` and `enroll`. `listItems` takes `reference` or `reference_prefix`. Metadata (at most 20 keys of `a-z 0-9 _`, up to 40 characters, each value a text of at most 500 characters, a number or a boolean), an update with no field, and a filter off the reference pattern or both filters together are refused before anything is sent, as the API answers them.
- Every error has `details`: the body's `detail.details` when it is an object, else `null`. An enrollment's 529 whose `details.reason` is `enrollment_unpriced` is never retried.
- A decision whose boosters name `ocr` waits 30 s per attempt unless `timeout` is set, and is never retried after a timeout, since the server finishes that attempt and may bill it; its other retries stay.
- Several places in one answer: `point()` and `box()` take `max` (2 to 16), sent only when given, and such a question is answered with a `PointsAnswer` or `BoxesAnswer` (`count`, `present`, `complete`, `points` or `boxes` with each place's `confidence`, `image`, `width`, `height`), told apart by the answer's own list. `max` is checked before sending (a whole number, 2 to 16); whether a model answers several places (`places.max_places` in `models()`) is the API's to judge, and a model that does not answers with its `ValidationError` (`not_supported`).
- `Batch.priceFactor` is gone. The API does not send it: the batch price is each model's `batch_price_factor` in `models()` (none on a fine-tuned model), and each line's charge is in its usage.
- `ModelInfo.pricePerMillionInput`, `pricePerMillionOutput`, `pricePerMillionImage`, `pricePerMillionVideo` and `batchPriceFactor`: the entry's prices as sent, each `null` when it states none (a fine-tuned model states no `batch_price_factor`). `limits` and `raw` keep them too.
- Device keys as `client.keys`, for a Manage device keys key: `create` (a Decisions-only key and its secret, `POST /v1/keys`, with an `Idempotency-Key`: the caller's `idempotencyKey`, else a new UUID per call, the same on every attempt; retried also on a 409 `idempotency_in_progress`), `list` and `all` (by `labels`, `deviceId` and `status`, a page of 1 to 200), `update` (only the fields given; `null` clears `labels`, `limits`, `dailySpendCap` or `expiresAt`), `revoke` and `revokeByLabels` (with `deviceIds` and `dryRun`). Each returns the API's object as sent. A malformed `idempotencyKey`, a label filter, a device id, a `status`, a `limit` and an update with nothing to change are refused before sending with the API's messages.
- Per-key usage as `client.usage` (suite 1.18): `key` (`GET /v1/keys/{key_id}/usage`), `list` (`GET /v1/usage`, one page) and `all` (every page, `next_cursor` followed until it is `null`), each returning the API's object as sent and retried as any read. The query's rules (`granularity`, `groupBy`, labels, `deviceId`, key ids and at most 100 of them, `scope`, `status`, `includeEmpty`, `limit`) are checked before sending with the API's messages. The conformance driver reads `query_all`; `CONFORMANCE_REF` is on suite 1.19.
- A 429 `key_spend_cap_reached` (a key past its daily spend cap) is thrown at once and never retried: the cap resets at 00:00 UTC. It stays a `RateLimitError` with `details` `resets_at`, `cap` and `spent`. A publishable key's 403 `origin_not_allowed` and `model_not_allowed` (with `details.allowed`) and its 429s with `details.reason` `client_rate` or `in_flight` are read as sent, as the README now says.

## 0.2.0 (unreleased)

Implements version 1.2 of the DecisionNode SDK specification (`SPEC_VERSION` is `"1.2"`) and passes conformance suite 1.10.

- Videos sent as frames: `new Video(id, frames, { fps, start, end })` and `new VideoFrame(t, data, mediaType?)`, taken as `videos` by `decide`, `check`, `classify`, `score`, `number`, `gate`, `decideMany` requests, batch requests and `checkRequest`. A frame's data is bytes (its type read from the first bytes) or base64 text with its media type. Frames always go inline; `fps`, `start` and `end` are left out of the request when not given.
- Before anything is sent: ids unique across images and videos, frame times of at least 0 and strictly increasing, JPEG, PNG or WebP frames, `fps` above 0 and at most 4, and `end` after `start`, each throwing `BadRequestError` with the API's message. More than 4 videos throws the API's `ValidationError` (a `too_long` entry on the videos). Frame counts are the API's.
- `Decision.usage.videoFrames` and `Decision.usage.videoSeconds` (`null` when absent) and `Decision.warnings` (an empty array when absent).
- The `point` and `box` question types: `point(instructions, image?, units?)` and `box(instructions, image?, units?)`, answered by `PointAnswer` (`x`, `y`) and `BoxAnswer` (`x1`, `y1`, `x2`, `y2`), each with `present`, `confidence`, `image`, `width` and `height`, typed from the questions. A request with one needs an image, and `image` names one of the request's images (required with two or more); with `units` these are checked before anything is sent and throw `ValidationError` with the API's entries.
- A request holds up to 16 images (4 before); a 17th throws the API's `ValidationError` before anything is sent: a `too_long` entry on the images, listed with the request's other entries, a local image in its `input` without its bytes. Up to 16 images are uploaded through one presign; `upload()` of more throws `BadRequestError` (`files: 1 to 16 files, got 17.`). `MAX_IMAGES` is 16.

Removed: `systemone()`. `POST /v1/systemone` is not part of the API; every decision is sent to `POST /v1/decide`, and `checkRequest` takes `decide`, `openSession`, `batches.create` and `batches.add`.

## 0.1.0 (unreleased)

First version. Implements version 1.1 of the DecisionNode SDK surface: decisions with `truth`, `choice`, `score` and `number` questions, `/v1/systemone`, the models list, image uploads, sessions and the Batch API.

- `DecisionNode` client: `decide`, `decideMany`, `systemone`, `check`, `classify`, `score`, `number`, `gate`, `models`, `upload`, `openSession`, `supervise`, `batches`, `runBatch` and `decideRaw`. The helpers take `images` and `model` like `decide`.
- `number(instructions, min, max, step)` and `NumberAnswer` (`number`, `expected`, `confidence`, `probabilities` keyed by each value as the API wrote it). A grid field left out is left out of the request.
- An answer the API sends under the older wire name of `truth` is read as a `TruthAnswer` whose `type` is `truth`.
- `systemone` sends `POST /v1/systemone` with the model always set and each `truth` question written with the type name that path takes.
- Images by URL pass through after a local check (`https`, at most 2,048 characters), the recommended input. Images from a path, bytes or base64 are checked locally (JPEG, PNG or WebP by their first bytes, a declared type that must match, 10 MiB, 40 megapixels read from the image header), then sent inline when the request's local images total under `DEFAULT_INLINE_THRESHOLD` (524,288 bytes, the `inlineThreshold` option) and uploaded at or above it: one presign for the request, the PUTs in parallel with exactly the storage's headers, then the upload id. `Image.fromBase64` and `Image.fromUploadId` are new.
- An in-memory cache keyed by the SHA-256 of an image's bytes reuses an upload, whatever its size, until 5 minutes before it expires (at most 256 entries). Concurrent requests with the same bytes share one upload. A request whose placed upload went stale uploads again and is resent once.
- Every fixed rule the API documents is checked before anything is sent: question shapes and field types, unknown question types (and `number` on `systemone`), choice, score, truth and number limits, every number grid rule in exact decimals, the 128-level nesting limit, images (ids, formats, size, pixels, an upload id's media type), image URLs (`https`, length, user information, port 443, reserved literal addresses), session `window` and `ttl_seconds`, session frames, batch `customId` rules and `batches.list` paging. A fault throws exactly what the API would answer: the same class and `errorType` (none for the API's plain-string 400s, `api_usage_error`, `image_url_refused`), its documented message, and for a 422 a `ValidationError` with the API's own `entries`; with no status and no request id. In `decideMany` and batches it is thrown for the whole call; `Session.send` throws it with nothing written and no `seq` used.
- Limits only `/v1/models` states (number support, sessions served, the largest window and lifetime, requests per batch, `customId` length, and restated bounds such as choice options) are checked once `models()` has been called on the client, and left to the API before that.
- `checkRequest(method, request)` for `decide`, `systemone`, `openSession`, `batches.create` and `batches.add`, and `Session.checkFrame(frame)`: every local check sending would run, held limits included, with the same error; nothing is sent or uploaded.
- Held `/v1/models` limits apply to a model named by an entry's `name`, else by an entry that states it as its `alias` or pinned `version`.
- `uploadTimeout` (default `DEFAULT_UPLOAD_TIMEOUT`, 60 seconds): each storage PUT attempt's own timeout, apart from `timeout`.
- `webSocketOptions` for the session socket's proxy and TLS settings (a dispatcher on Node 22+, `ws` options on Node 20, `proxy` and `tls` on Bun); settings that turn certificate checks off are refused. On Node 22+ the socket follows the global dispatcher `fetch` uses; on Bun it is given the proxy `fetch` reads from the environment.
- Batch results are read from the network line by line, the whole file, never paged.
- A `clock` option: the time upload URLs and cached uploads are judged by. A PUT answered `403` after its URL's 5 minutes is presigned again once; a second such `403` is thrown.
- Sessions: `openSession`, `Session.connect`, `send`, `replies`, `next`, `end`, and `supervise`, with `Reply`, `FrameError` and `SessionClosed` values. `SessionLimitError`, a `RateLimitError`, for a `429` `session_limit_exceeded`, never retried. Node 22+, Deno and Bun use their own WebSocket; Node 20 uses the optional `ws` dependency.
- The Batch API: `batches.create`, `add` (split into calls of at most 10 MiB), `finalize`, `get`, `list`, `results` (streamed line by line) and `cancel`, and `runBatch`. Create, add and finalize retry only on 429 and 529.
- `gate` asks three fixed questions, worded the same in every DecisionNode SDK.
- Result types `Decision`, `DecisionResult` (one entry of `decideMany`), `ModelInfo` (one entry of `models()`) and `UnknownAnswer` (an answer of a type this version does not know).
- Empty strings for `apiKey`, `baseUrl` and `model` count as not given. `decideMany` checks every request before sending any: a `concurrency` below 1 throws a `RangeError`, an invalid request a `TypeError`, and nothing is sent.
- A missing token count or latency is `null`, never 0.
- Question builders `truth`, `choice`, `score` and `number`; plain wire-form question objects work anywhere a builder does.
- Answer types inferred from the questions: `choice` answers are typed with the union of their option names.
- A file image is read when the `Image` is made; an unreadable file throws a `TypeError` there. Its media type, and that of bytes given without one, is taken from the first bytes.
- Timeouts, retries on 408, 429, 5xx, timeouts and connection errors, honouring `retry-after-ms` and `Retry-After` (seconds or an HTTP date), capped at 60 seconds. A `sleep` option replaces the wait in tests.
- Only 200 to 299 is a success. Redirects are never followed; a 3xx is an error.
- A caller's `fetch` cannot be inspected, so it is refused with a `TypeError` when the client is made unless `fetchHonoursManualRedirect: true` confirms it honours `redirect: 'manual'` and keeps TLS checks on. It is still called with `redirect: 'manual'`, and a response it reports as redirected, as an opaque redirect, or from another URL is refused, its body never read.
- With `NODE_TLS_REJECT_UNAUTHORIZED=0`, an `https` base URL (the scheme in any case, `HTTPS://` included) is refused with a `TypeError`, when the client is made and before each request. A process-wide dispatcher that turns off certificate checks cannot be detected and is the caller's responsibility.
- The base URL must be `https`; `http` only for `localhost`, `127.0.0.1` and `::1`. Anything else throws a `TypeError` when the client is made.
- `timeout` must be above 0 and `maxRetries` a whole number 0 or more, else a `RangeError`. The timeout covers the whole attempt, from sending to the last byte of the body.
- Local argument problems (an empty question map, an unserialisable value, an unreadable image file, a bad base URL, timeout, `maxRetries`, `inlineThreshold`, `concurrency` or `pollInterval`) throw JavaScript's own `TypeError` or `RangeError`, never a `DecisionNodeError` subclass.
- An answer of a known type with a field missing or of the wrong type is an `UnknownAnswer` with its raw fields; the decision does not fail.
- `check`, `classify` and `score` throw `ServerError` (with the status, `requestId` and `reason`) when their own answer is missing or malformed; `decide` returns an `UnknownAnswer` for it.
- An error with no server message has `message` `""`.
- Typed errors under the exported base class `DecisionNodeError`, including `RefusalError`, `PermissionDeniedError`, `ContextLimitError`, `ValidationError`, `RateLimitError` and `OverloadedError`. A status without its own class is `DecisionNodeError` itself. An error's `message` is the API's own message; `reason` is the API's explanation from the `x-decisionnode-error` header.
- `SPEC_VERSION` (`"1.1"`) and `User-Agent: decisionnode-node/<version>`.
- `decision.safety`, parsed from the `x-decisionnode-safety` response header. The README documents the `x-decisionnode-safety-body` request header.
- ESM, CommonJS and TypeScript declarations. Runs on Node 20.16+, Deno, Bun and edge runtimes with `fetch`; sessions need a runtime whose WebSocket can send an `Authorization` header.
